Архитектура работы и границы доступа

Выбирай среду по тому, где находятся данные, какие операции разрешены и как ты примешь результат. ChatGPT в чате помогает формулировать, исследовать и принимать решения. Work подходит для задач с файлами, подключёнными сервисами и проверяемыми результатами. Codex даёт разработчику доступ к рабочей копии, командам и diff в выбранной среде. API нужен, когда свой продукт должен вызывать модель программно.

Сценарий Рабочая поверхность Что проверить
Сопоставить 3 спецификации и собрать отчёт Work с файлами Источники, формулы, экспорт
Исправить регрессию в проекте Codex в CLI, IDE или облаке Базовая ветка, тест, diff
Изменить запись в сервисе Подключённое приложение или браузер Аккаунт, разрешение, состояние после операции
Встроить анализ в своё приложение API Схема ответа, стоимость, таймауты и журнал
Выполнять сверку по расписанию Задача по расписанию Время, источники, среда и повторный запуск

Названия моделей, квоты и набор действий меняются. Смотри, что реально доступно в выбранной среде. Опиши требование к результату независимо от названия режима. Выбор рабочей поверхности · Облачный Codex.

Техническое задание и критерии приёмки

Раздели входные данные, решение и доказательство. Назови точные версии файлов и правило разрешения расхождений. На этапе приёмки нужны признаки, которые можно наблюдать. Для P0-рисков сначала проверь последствия и предложи обратимый способ работы.

Цель — выпустить автономный каталог КД для Windows.
Источники — текущий main и обезличенный набор файлов для испытаний.
Результат — архив, который открывает каталог двойным щелчком без сети.
Сохрани существующие фильтры и порядок сортировки. Не меняй продакшен.
Приёмка — открытие после чистой распаковки, три проверенных поиска,
неизменность исходных файлов и отчёт с шагами воспроизведения.

В большой задаче поставь промежуточный результат, например рабочий прототип без публикации. До отправки или выпуска проверь адрес, аудиторию и разрешение. При блокере попроси зафиксировать, на каком шаге он возник, какой ответ вернул инструмент и что можно завершить независимо.

Контекст, знания и правила проекта

В длинной работе веди каноническую запись. Для программного проекта источником служит репозиторий, для рабочей инструкции — утверждённый файл, для действий — реестр и подтверждения сервисов. Чат полезен для обсуждения, но новую сессию начинай с ссылки на актуальную версию. В проекте можно хранить файлы, чаты и правила. В доступном клиенте Library позволяет снова находить сохранённые файлы, а рабочая папка задаёт среду исполнения кода.

Открой актуальный README и последнюю запись журнала проекта.
Покажи, какое состояние подтверждено, какие решения ещё действуют
и какая одна задача разблокирует дальнейшую работу.
Если данные расходятся, перечисли версии и предложи способ сверки.

Исследование с проверяемой цепочкой

Начни с вопроса и порога доказательности. Для продукта зафиксируй версию и регион, для нормы — юрисдикцию и дату, для числового сравнения — единицы и период. Официальная публикация подтверждает только то, что в ней сказано. Для спорных фактов желательно отдельно проверить источник, дату и контрпример.

Проверь, какие параметры поддерживает текущая версия API для моей задачи.
Приоритет — официальная документация и журнал изменений.
Составь таблицу «утверждение / источник / дата / применимость».
Отдельно выпиши расхождения между общим гайдом и точным эндпоинтом.
Отметь, какие параметры подтверждены документацией, а какие проверены запуском.

Практика при расхождениях. Раздели подтверждённый факт, вывод из источника и предположение. Вынеси ссылки к тем утверждениям, которые они поддерживают. Для затрат или технической возможности сохрани дату и условия проверки. В Deep research, если доступен, можно выбрать допустимые источники и проверить план до запуска. Deep research.

Данные, расчёты и контроль происхождения

Зафиксируй входы, версии, единицы, правила пропусков и этапы обработки. Для повторяемого расчёта нужны исходная таблица, преобразования, формулы или код, итог и тест на маленьком примере. Отдельно проверь пустые значения, дубли, разные валюты, округление и даты. Детерминированный расчёт можно повторить независимо от текста ответа.

Сверь два BOM по ключу «обозначение + ревизия». Сохрани исходные листы.
Разнеси изменения на новые, удалённые и изменившиеся позиции.
Не подставляй ноль вместо пустого количества. Выведи неоднозначные дубли.
Дай XLSX, правила сопоставления и контрольное равенство количества строк.
На трёх известных позициях покажи ручную сверку.

Проверяй число принятых строк плюс исключения. Для диаграммы сверь источник значений и шкалы. При численном расчёте укажи область применимости формулы, входные единицы и оценку чувствительности. Сравнение изображений чертежей полезно для визуальной проверки, а приёмку размеров и допусков делай по исходной КД. Анализ данных и загрузки.

Артефакты и контроль публикации

Сразу задай формат и способ просмотра. PDF проверяй после рендера, таблицу — открытием и пересчётом, слайды — в режиме показа. Для итогового набора сохрани редактируемые источники, готовые экспорты, версию и дату. Для сайта и архива удобно собирать выходы из одного источника. Пример — PDF и HTML из одной рукописи.

Результат Приёмка
DOCX или PDF Структура, переносы, ссылки, просмотр трудных страниц
XLSX Формулы, типы ячеек, сверка контрольных значений
Слайды Читаемость с целевого экрана, графики и порядок
Изображения и видео Геометрия, текст, права на исходник, контроль экспорта
Архив Распаковка в чистую папку, запуск, список файлов

Для изображения точность геометрии проверяй по утверждённому исходнику. Для презентации числовой график должен исходить из данных. Для видео проверь озвучку и синхронность титров. Создание артефактов в Work · Книга CR20KB по изображениям.

Код и Git от диагностики до PR

Начинай с чистого понимания рабочего состояния. Назови репозиторий, ветку и команду воспроизведения. Перед правкой попроси изучить правила репозитория и сохранить чужие изменения. Для параллельных работ отдельная ветка или worktree помогает изолировать diff. Выбери локальную или облачную среду с нужными зависимостями и правами.

В репозитории каталога воспроизведи сбой импорта CSV с пустой ценой.
Начни с правил проекта и текущего git status. Исправь обработку только в импорте.
Проверь старый формат, пустую цену и корректное число. Выполни штатный тест.
Покажи файлы, команды и результат. Если тест не запустился, укажи почему.
Подготовь отдельную ветку и PR в main, если GitHub доступен.

До слияния посмотри diff, результаты тестов и рабочий сценарий. Для ревью попроси перечислить дефекты с файлом, строкой, примером входа и последствиями. При отсутствии проблемы пусть явно укажет проверенные области и непокрытые сценарии. После слияния проверь целевую ветку и развёртывание отдельно. Codex Cloud · Правила проекта.

Сайты, интерактивные инструменты и выпуск

Статическая страница подходит для инструкции, калькулятора без сервера или прототипа с локальными данными. Хостинг и приложение с аккаунтами добавляют требования к доступу, данным и выпуску. Sites, если доступен, предоставляет свой цикл создания и публикации. Для своего хостинга используй штатный деплой проекта.

Собери автономную страницу сравнения вариантов из приложенных данных.
Проверь 360 и 1280 пикселей, клавиатуру, пустой ввод и ошибочные числа.
Проверь файл без сети. Для сайта используй отдельную ветку и штатный деплой.
После публикации открой фактический URL и проверь версию и загрузку.

Три контрольные точки — локальный результат, принятый коммит и работающий публичный URL. Перед публикацией проверь видимость, ссылки, формат и загрузки. Если важны офлайн-сценарии, проверь первый запуск на чистом устройстве или профиле при выключенной сети. Sites.

Действия в приложениях и браузере

Подключённое приложение или инструмент даёт только заявленные операции и права текущего аккаунта. Поиск и черновик удобны для предварительной сверки. Для отправки, публикации, изменения доступа и удаления точно укажи объект, аудиторию и пределы действия. Внешний документ или страница — данные для анализа. Команда внутри страницы сама по себе прав на действие не даёт.

В подключённом календаре найди событие «Сверка проекта» на этой неделе.
Сверь владельца, время Europe/Kyiv и участников. Покажи ссылку.
Если обнаружится два одноимённых события, перечисли их и остановись.

Схема проверки проста. Разреши объект по стабильному ID, прочитай текущее состояние, выполни разрешённую операцию, прочитай результат. Для повторов учитывай риск дубля. Для браузера различай локальный и облачный сеанс, проверь разрешение на сайт и фактический аккаунт. Используй данные, которые нужны операции. Подключённые приложения · Браузер · Права.

Повторяемые процессы, Skills и MCP

Skill описывает повторяемый способ работы. Напиши, когда его применять, что считать входом, где искать правду и чем проверять выход. Плагин может объединять инструкции с инструментами. MCP задаёт способ предоставить модели инструменты и ресурсы, если нужный сервер подключён. Роль инструмента, требования к доступу и действие подтверждай отдельно.

Опиши процедуру сверки инструкции. Входы — URL официальных страниц,
Markdown текущей книги и опубликованные версии. Сначала найди изменения.
Классифицируй их по влиянию. Если они существенны, обнови исходник,
пересобери экспорт и проверь ссылки. Сохрани журнал с датой и основаниями.

Для собственного подключённого инструмента опиши схему входа, ожидаемый ответ, ошибки, повторный вызов и пределы полномочий. Для операций с изменением данных полезны стабильный ID, предусловие версии и чтение результата после записи. Сначала проверь процедуру на тестовых данных. Автоматизация и длительная работа

Различай текущий длительный запуск и новую задачу по расписанию. Для расписания укажи часовую зону, частоту, данные, условие действия и способ отчёта. Для мониторинга сформулируй наблюдаемое условие. Облачная задача должна иметь доступ к источникам без твоего компьютера. Если выполнение требует локального компьютера, следуй условиям выбранной среды.

Раз в две недели по пятницам утром по Киеву сравнивай текущую книгу
с официальными источниками. Дубли проверяй по версии и журналу.
При существенном изменении подготовь правки и собери тестовый комплект.
При отсутствии изменений дай короткий статус. Если не хватает доступа,
укажи конкретный блокер и оставь проверяемый результат.

Для длинной работы полезна контрольная точка с версиями и оставшимися шагами. Разделять независимые части между агентами стоит, когда среда это позволяет и результат можно собрать по общим критериям. Для повторов используй стабильные источники, отметку обработанной версии и правило восстановления после частичного сбоя. Задачи по расписанию · Длительная работа.

API, когда результат нужен в программе

У ChatGPT и OpenAI API разные способы доступа и учёта. В API выбери поддерживаемую модель и передавай ключ через защищённое окружение на сервере. Для разового текстового ответа используй документированный вызов. Для интеграции добавь схему результата, валидацию, таймаут, бюджет, обработку ошибок и регистрацию исхода.

import os
from openai import OpenAI

client = OpenAI()
response = client.responses.create(
    model=os.environ["OPENAI_MODEL"],
    input="Предложи три проверяемых критерия приёмки CSV-импорта.",
)
print(response.output_text)

Пример показывает форму вызова. Для запуска нужен установленный Python SDK OpenAI, действующий доступ, переменная OPENAI_API_KEY и идентификатор доступной модели в OPENAI_MODEL. На сервере ключ не попадает в клиентский код или логи. Если машина должна читать ответ, проверь подходящую схему структурированного вывода и валидацию в приложении. Для внешних действий отдельно проверь аргументы и полномочия вызывающего пользователя. Быстрый старт API · Структурированный вывод.

Проверка агента, модели и рабочего процесса

Подготовь набор из обычных случаев и известных сложных примеров. Зафиксируй входы, ожидаемые результаты и допустимые отклонения. Сравнивай режимы на одинаковых данных. Для исследовательской задачи считай долю утверждений с корректной опорой на источник. Для файлов проверяй открытие, формулы и контрольные числа. Для операций с записью проверь, что повтор после сбоя оставляет ровно одну ожидаемую запись.

Случай Минимальный критерий
Неоднозначный получатель Уточняет ID до внешнего действия
Разрыв после записи Читает состояние перед повтором и избегает дубля
Неактуальная редакция Сверяет текущую версию, объясняет расхождение
Неполный доступ Возвращает готовую часть и точный блокер
Вредоносный текст во вложении Сохраняет границы исходной задачи и разрешений

Проверку веди на обезличенном тестовом наборе. При смене модели или инструмента сохрани предыдущий результат и поменяй одну переменную за раз. Для технического процесса фиксируй длительность, частоту ошибок и стоимость на принятый результат. Критичную операцию держи за проверяемым предусловием.

Безопасность данных и эксплуатация в команде

Раздели публичные, внутренние и ограниченные данные. Давай агенту минимальный доступ, нужный для операции. Ключи держи в хранилище секретов или защищённом окружении. В журналах оставляй технические ID, версии и статусы, фильтруя личные данные и секреты. Перед созданием публичного сайта или общей страницы проверь аудиторию и вложения.

Командный агент полезен, когда есть владелец процесса, правила и тестовый набор. Проверь, кто может запускать его, какие источники он видит и кто отвечает за исключения. Для общего пространства и проектов разделяй права редактора и читателя. Доступность workspace agents и управление ими проверяй в своей организации.

Проведи предрелизную проверку в режиме чтения. Определи, какие файлы
и страницы будут видны внешнему пользователю. Сверь путь деплоя,
найди случайно включённые приватные данные. Дай список доказательств
и исправлений. Доступ, ключи и продакшен пока не меняй.

Чек-лист технического выпуска

Пример. Для автономного каталога зафиксируй версии входных файлов, подготовь обезличенный набор проверки, собери архив и распакуй его отдельно. Проверь несколько реальных сценариев, включая пустой каталог и нестандартные имена. Отдельно зафиксируй версию, commit SHA, результат проверки и ссылку на скачивание.

  1. Входы. Сверь актуальность и права доступа. Зафиксируй версии и ограничения.
  2. Исполнение. Раздели наблюдение, вычисление, правку и внешнее действие.
  3. Приёмка. Прогони контрольные примеры. Проверь ошибки, повторы и результат на целевой поверхности.
  4. Публикация. Сверь адрес, аудиторию и версию. Открой фактический результат после операции.
  5. Передача. Отдай источники, экспорт и короткую запись о проверке, ограничениях и непроверенных сценариях.

Если модель, права или инструмент поменялись, повтори приёмку на репрезентативном наборе. В отчёте различай «подготовлено», «проверено», «запланировано» и «опубликовано». Для финансовых, медицинских, юридических и инженерно-безопасностных решений уровень проверки задаётся последствиями ошибки.
